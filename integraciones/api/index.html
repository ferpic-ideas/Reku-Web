Empezá acá

Inicio rápido

La API es server-to-server. El token debe permanecer en tu backend y nunca incluirse en JavaScript público, una app móvil ni una URL.

Demo de integración Artro

Probar el recorrido completo ↗ (acceso libre, sin clave). Es un ejemplo con la API real de Reku: la cuenta registrada, el email validado y el pago externo se simulan; los turnos sí se crean en Reku. No realiza cobros ni modifica el sitio de Artro. Incluye agenda, orden médica, confirmación, sala de espera, reprogramación, cancelación y un panel de llamadas a la API. En producción reemplazá los datos editables por tu sesión autenticada y validá el pago en tu backend.

Primero consultá GET /agreement: devuelve type (Pago o Nomina), slug (también subdominio), direct_treatment, treatment_service_id, medical_order_required e identifier_label. Ambos tipos permiten gestionar credenciales desde Admin → Acuerdos → API.

Los ejemplos de abajo muestran Pago sin orden obligatoria. Para Nómina y carga de órdenes, consultá las variantes del flujo más abajo.

Acceso, correo y comunicación

En Admin → Acuerdos seleccioná Acceso: API y elegí Comunicación: Reku o Integrador. Cobranded y Logo siguen disponibles para personalizar la sala de espera y las pantallas de Reku. No se piden PDF “Cómo funciona” ni enlaces de pago; el cobro de los acuerdos Pago ocurre en tu plataforma. Ambos tipos, Pago y Nómina, permiten integración. Las credenciales emitidas anteriormente siguen vigentes hasta revocarlas, aunque el acuerdo aún figure como Web Reku.

GET /agreement devuelve access_mode, communication_sender, email_verification_required=false y email_verification_responsibility=integrator. La API no verifica la titularidad del email: el integrador debe hacerlo antes de confirmar y de entregar enlaces privados. Reku valida el formato, no la identidad del dueño de la casilla.

Con Acceso API, las nuevas reservas se realizan desde el sitio del integrador, no desde el formulario público de Reku. Los enlaces privados para gestionar turnos existentes y entrar a la sala de espera siguen funcionando.

Con Comunicación Reku, enviamos los correos del turno. Con Integrador, no enviamos al paciente confirmaciones, recordatorios, reprogramaciones ni cancelaciones; tu plataforma debe gestionarlos. Los avisos al profesional y correos de seguridad del portal se mantienen. Para detectar cambios realizados desde Reku, consultá periódicamente GET /appointments o el detalle: todavía no hay webhooks.

Base URL https://www.reku.io/api/partners/v1
1

Ver prácticas habilitadas

Obtené el catálogo disponible para tu acuerdo.

curl https://www.reku.io/api/partners/v1/services \
  -H "Authorization: Bearer rku_ag_REEMPLAZAR"
2

Consultar disponibilidad

Buscá horarios para una práctica en un rango de fechas.

curl "https://www.reku.io/api/partners/v1/availability?service_id=2&from=2026-09-01&to=2026-09-07" \
  -H "Authorization: Bearer rku_ag_REEMPLAZAR"
3

Pre-reservar durante 10 minutos

Protegé el horario mientras completás el pago en tu plataforma.

curl https://www.reku.io/api/partners/v1/holds \
  -X POST \
  -H "Authorization: Bearer rku_ag_REEMPLAZAR" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: hold-ORD-90821" \
  -d '{
    "service_id": 2,
    "professional_id": 7,
    "date": "2026-09-03",
    "start_time": "15:30"
  }'
4

Confirmar un turno pagado

Después del pago, creá la reserva usando el hold_id recibido.

curl https://www.reku.io/api/partners/v1/appointments \
  -X POST \
  -H "Authorization: Bearer rku_ag_REEMPLAZAR" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: reserva-ORD-90821" \
  -d '{
    "external_id": "ORD-90821",
    "hold_id": "hold_REEMPLAZAR",
    "payment_reference": "PAY-44339",
    "patient": {
      "first_name": "Ana",
      "last_name": "Pérez",
      "email": "ana@example.com",
      "phone": "+5491160000000"
    }
  }'
✓

Una respuesta 201 Created confirma el turno. La pre-reserva vence automáticamente a los 10 minutos, pero si el pago tarda más y nadie tomó el horario, la confirmación continúa normalmente.

02
Buenas prácticas

Seguridad

🔒

Siempre HTTPS

Autenticá cada solicitud con Authorization: Bearer ….

◉

Datos aislados

Cada credencial sólo accede a los recursos de su propio acuerdo.

↻

Rotación simple

Los tokens pueden coexistir durante una rotación y revocarse desde el Admin.

⌁

Límites seguros

El rate limiting funciona por credencial e IP e informa Retry-After.

No expongas el token.Guardalo en un secret manager o variable de entorno protegida. Nunca lo registres en logs ni lo envíes al navegador.

El acuerdo debe informar al paciente que compartirá sus datos con Reku para gestionar el turno.

03
Implementación

Flujo recomendado

  1. 1
    Leé los requisitos del acuerdo

    Consultá GET /agreement y GET /services.

  2. 2
    Elegí el horario

    Consultá profesionales o directamente la disponibilidad.

  3. 3
    Protegé el horario

    Ejecutá POST /holds. Reku lo retira de disponibilidad durante 10 minutos y devuelve un hold_id.

  4. 4
    Completá los datos

    En Pago, cobrá en tu sistema. En Nómina, pedí el identificador indicado por el acuerdo. Adjuntá la orden si corresponde.

  5. 5
    Confirmá la reserva

    Ejecutá POST /appointments con el hold_id. En Pago, un 201 significa turno confirmado y pago externo declarado. En Nómina significa turno confirmado con cobertura de nómina, sin cobro.

  6. 6
    Guardá los identificadores y enlaces privados

    Persistí data.id, tu external_id y data.links. Mostrá o enviá los enlaces sólo al paciente validado.

  7. 7
    Gestioná cambios

    Reprogramá con PATCH /appointments/{id} o cancelá con POST /appointments/{id}/cancel.

Vencimiento automático:al cumplirse 10 minutos el horario vuelve a ofrecerse sin intervención. La confirmación posterior vuelve a comprobar disponibilidad y requisitos actuales del acuerdo.

Tratamiento directo

Si direct_treatment=true, salteá la selección de práctica y profesional. /services sólo devuelve el tratamiento configurado; en disponibilidad y holds podés omitir service_id. Otro servicio se rechaza. Se ignora professional_id y se asigna automáticamente un profesional habilitado. Consultá disponibilidad y ofrecé primero el horario más cercano; la API no elige la fecha por el paciente.

Acuerdos de Nómina

Usá identifier_label como etiqueta (por ejemplo, DNI o legajo; si está vacío, Identificador). Enviá patient.identifier junto con nombre, apellido, email y teléfono. Se valida contra la nómina de ese acuerdo, sin distinguir mayúsculas; un identificador de otro acuerdo no sirve.

{
  "external_id": "NOM-90821",
  "hold_id": "hold_REEMPLAZAR",
  "patient": {
    "first_name": "Ana", "last_name": "Pérez",
    "email": "ana@example.com", "phone": "+5491160000000",
    "identifier": "LEGAJO-123"
  }
}

La respuesta indica payment.status=nomina, payment.provider=nomina, monto cero y settlement.billable=false. No se declara pago externo; payment_reference se ignora. La cancelación no genera devolución. Las liquidaciones siguen siendo exclusivas de Pago.

Orden médica obligatoria u opcional

Para enviar la orden, usá multipart/form-data: el campo payload contiene el JSON anterior y medical_order contiene un archivo PDF, JPG, PNG o WebP de hasta 10 MB. Se comprueba tipo y firma del archivo. JSON sin archivo sigue disponible si el acuerdo no exige orden.

curl https://www.reku.io/api/partners/v1/appointments \
  -H "Authorization: Bearer rku_ag_REEMPLAZAR" \
  -H "Idempotency-Key: reserva-NOM-90821" \
  -F 'payload=<reserva.json' \
  -F 'medical_order=@orden.pdf;type=application/pdf'

Reintentá con el mismo JSON y archivo usando la misma clave. La huella del archivo forma parte de la idempotencia: cambiarlo con esa clave devuelve conflicto. La orden queda privada y disponible para el admin y el profesional asignado. medical_order.received significa recibida, no validada clínicamente.

Enlaces de confirmación y cuestionario

POST /appointments devuelve data.links.manage_url (gestionar turno), data.links.waiting_room_url (sala) y data.links.expires_at. Guardalos en tu backend de forma privada, sin logs ni analytics. Son accesos personales: no los compartas con otros pacientes. La sala respeta el horario habilitado del turno.

No necesitás desarrollar una sala de espera: un botón “Ingresar a la videollamada” puede abrir waiting_room_url, que muestra la sala de Reku y controla el acceso a Meet. La API de partners todavía no expone presencia del profesional ni habilitación en tiempo real para construir una sala propia.

Los enlaces se devuelven al crear y al reintentar la misma operación con su Idempotency-Key; GET, PATCH y el listado no los generan. El replay conserva la respuesta y el vencimiento originales, no los renueva. Consultá GET para el estado actual del turno.

Confirmaciones y recordatorios del integrador

Con Acceso: API y Comunicación: Integrador (access_mode=api, communication_sender=integrator), tu backend se encarga del envío y la programación de confirmaciones, recordatorios, reprogramaciones y cancelaciones al paciente. Reku no duplica esos correos; los avisos al profesional y los correos de seguridad del portal se mantienen.

  1. Al confirmar con POST /appointments, guardá data.id, data.external_id, data.patient, data.service, data.professional y data.schedule: incluye date, start_time, end_time y timezone. Estos datos permiten armar el contenido del mail y programar el recordatorio en la zona horaria correcta.
  2. Guardá también data.links.manage_url, data.links.waiting_room_url y data.links.expires_at, asociados al turno y al usuario validado. Usá los botones “Gestionar mi turno” e “Ingresar a la videollamada” con esos enlaces. Son privados: protegélos en tu backend, sin logs ni analytics.
  3. Antes de cada recordatorio, consultá GET /appointments/{id}: enviá sólo si status=confirmed y el turno sigue siendo futuro. Si cambió el horario, actualizá el mensaje y su programación; si se canceló, cancelá el recordatorio. Registrá los envíos para evitar duplicados.
  4. Todavía no hay webhooks. Para enterarte de cambios hechos desde Reku, consultá periódicamente el detalle de los turnos guardados o GET /appointments con su paginación. Compará status, schedule, professional y updated_at; no uses el replay de creación como estado actual.
Limitación actual: renovación de enlaces pendiente.Reprogramar con PATCH no renueva ni devuelve los enlaces originales. Si el turno se mueve a una fecha posterior a data.links.expires_at, esos enlaces pueden vencer antes de la consulta. Hoy no hay un endpoint de renovación: no envíes enlaces vencidos ni prometas acceso para esa nueva fecha sin resolverlo con Reku. Repetir el POST original con la misma Idempotency-Key tampoco los renueva.

Alcance de la demo: /test muestra el recorrido de reservas y conserva sus enlaces por sesión, pero no implementa un servicio de mails ni un programador de recordatorios del integrador. Si el acuerdo tiene Comunicación: Reku, los correos que llegan son los habituales de Reku. En producción, el integrador debe implementar sus propios envíos y conservar los datos de forma persistente.

Cuestionario e integración interna

Las reservas por API no tienen cuestionario Reku: devuelven consultation_required=false y consultation_status=not_applicable. No muestres el bot ni envíes recordatorios para completarlo. Los estados pending, started y completed quedan por compatibilidad con turnos históricos. Los informes históricos completados se conservan.

La asignación a ReHub continúa internamente y su URL se guarda, independientemente de quién gestione la comunicación. La URL interna de ReHub y los PDF clínicos no se exponen a partners.

Cambios del turno

PATCH permite corregir datos y reprogramar, pero no reemplazar email ni identificador del paciente: cancelá y creá otro turno para evitar transferir documentación o enlaces privados. Si enviás patient, enviá todos sus campos. Se conserva el tipo económico y la condición de orden del turno original. En tratamiento directo se conserva el profesional salvo un cambio explícito a otro habilitado. PATCH no admite archivos.

04
Referencia

Endpoints

Todos los endpoints parten de la Base URL y devuelven JSON.

GET/agreement

Datos del acuerdo, zona horaria y capacidades habilitadas.

GET/services

Prácticas que tienen al menos un profesional activo asignado al acuerdo.

GET/professionals?service_id={id}

Profesionales habilitados para la práctica y el acuerdo.

GET/availability?service_id={id}&date=YYYY-MM-DD

Slots de un día. También admite from/to —máximo 31 días— y professional_id opcional.

POST/holds

Pre-reserva un horario durante 10 minutos. professional_id es opcional; si se omite, Reku asigna el primer profesional disponible.

POST/appointments

Confirma Pago o Nómina usando hold_id, datos del paciente y orden si corresponde. Acepta JSON o multipart con archivo.

GET/appointments

Lista paginada. Filtros: from, to, status, external_id, page y limit.

GET/appointments/{id}

Detalle de un turno propio del acuerdo.

PATCH/appointments/{id}

Corrige datos o reprograma, sin reemplazar la identidad del paciente. Requiere un nuevo Idempotency-Key.

POST/appointments/{id}/cancel

Cancela un turno futuro. Body: { "reason": "…" }. El acuerdo gestiona cualquier devolución en su sistema.

05
Observabilidad

Errores y reintentos

Todas las respuestas incluyen X-Request-Id. Conservá ese valor para que soporte pueda rastrear la operación.

{
  "error": {
    "code": "slot_unavailable",
    "message": "Ese horario ya no está disponible.",
    "request_id": "…"
  }
}
HTTPQué significaAcción
400JSON o Idempotency-Key inválido.Corregir la solicitud.
401Token ausente, inválido o revocado.Revisar o rotar la credencial.
404Recurso inexistente o ajeno al acuerdo.Revisar el ID.
409Horario ocupado tras vencer el hold, hold ya consumido o conflicto de idempotencia.Consultar disponibilidad o revisar la operación original.
422Datos válidos como JSON pero incorrectos.Corregir campos.
422identifier_required, identifier_not_eligible, medical_order_required o service_not_available.Revisar identificador, orden y configuración del acuerdo.
413 / 415Archivo demasiado grande o tipo/firma inválidos.Enviar un documento válido de hasta 10 MB.
409patient_identity_not_editable.Para otro paciente, cancelar y crear un turno nuevo.
429Límite temporal superado.Esperar Retry-After.
5xxError transitorio de Reku.Reintentar con la misma clave y backoff.
i

Un mismo Idempotency-Key con el mismo body devuelve la respuesta original y el header Idempotent-Replayed: true. Si se reutiliza con otro body, devuelve 409 idempotency_conflict.
